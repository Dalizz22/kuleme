# 接口契约约定

机器可读的接口定义在 [`api/openapi.yaml`](../api/openapi.yaml)，实现见 `server/internal/*/router.go`。本文只讲**跨接口的公共规则**（信封、状态码、幂等、权限、限制），避免同一件事在 100 多个端点上各写一遍。两者冲突时以 OpenAPI 与运行中的服务为准。

## 1. 基础约定

| 项目 | 约定 |
|---|---|
| 路径前缀 | 所有业务接口在 `/api/v1` 下；Web 与 Android 共用同一套接口，没有 BFF |
| 字段命名 | JSON 一律 `snake_case` |
| ID | 字符串、不透明，均为 UUID；客户端不得转成数字、不得从 ID 推导权限或顺序 |
| 时间 | 带时区的 RFC 3339 UTC 串（`2026-10-26T15:04:05Z`）；纯日期用 `YYYY-MM-DD` |
| 金额 | 精确十进制字符串，客户端不用浮点数计算 |
| 空值 | 修改请求里「字段缺省」= 不改；`null` 仅在允许清空的字段表示清空 |
| 版本 | 可编辑资源返回整数 `version`；修改时带 `expected_version`，冲突返回 `409 VERSION_CONFLICT` |
| 分页 | `page` 从 1 开始，`page_size` 默认 20、最大 100；列表返回 `{items, page, page_size, total}`，`total` 是**筛选后**的总数 |
| 追踪 | 服务端生成 `request_id`，响应体与 `X-Request-ID` 一致；日志不记录密码、令牌与 AI key |

成功结构与失败结构：

```json
{"data": {...}, "request_id": "0f3c…"}
{"error": {"code": "VERSION_CONFLICT", "message": "资料已更新，请重新获取", "details": {}}, "request_id": "0f3c…"}
```

HTTP 状态码反映成败，不用 200 包裹错误。文件下载直接返回文件流；异步受理返回 `202` 与任务对象。

## 2. 会话与权限

- Web 用**同源 Cookie 会话 + CSRF**；Android 用 `Authorization: Bearer <token>`，服务端只存令牌摘要，可撤销。
- 未登录的实例信息只含实例身份、API 版本与初始化状态；不暴露库存、用户列表或配置秘密。
- 401 → 回登录页；403 → 展示权限不足 / 功能关闭原因，**不注销**会话；网络失败 → 阻断业务并给重连入口。
- 403 与 404 的判据：对象在用户可见范围内但无权执行该操作 → **403**；对象根本不在可见范围（别人的私有库、他人私有文件）→ **404**。
- 注销是 `DELETE /api/v1/sessions/current`。
- 跨域：默认放行 `capacitor://localhost`、`http://localhost`、`https://localhost`，可用 `KLM_CORS_ORIGINS`（逗号分隔，整体替换）追加；允许的回显精确 Origin，**从不返回 `Allow-Credentials`**，非法来源的预检直接 403。开发环境（`KLM_ENV=development`）额外放行局域网与环回地址。

## 3. 写操作与幂等

有副作用、且可能被客户端重试的写操作使用 `Idempotency-Key` 请求头：客户端生成 UUID，**同一次重试期间保持不变**。服务端把它与「操作者 + 方法 + 路由 + 规范化请求体」绑定，因此：

- 同键同内容重放 → 返回**原状态码与逐字节相同的响应体**（含原来的 `request_id`），不重复执行业务；
- 同键不同内容 → `409 IDEMPOTENCY_CONFLICT`；
- 同键仍在处理中 → `409`，提示稍后重试；超过 5 分钟的残留由下一次请求接管；
- 键不是 UUID 或超过 128 字符 → 在落库前返回 `422 INVALID_IDEMPOTENCY_KEY`。

`operation_id` 就是客户端生成的这个键，原样出现在响应里，因此响应丢失后可以按它查询：

```
GET /api/v1/operation-results/{operation_id}
→ {"data": {"operation_id": "...", "status": "in_progress|succeeded|failed",
            "result": {...}, "error_code": "...", "created_at": "...", "updated_at": "..."}}
```

`result` 是成功响应的 `data` 本体；`error_code` 与失败响应的 `error.code` 同源。他人或未知的 `operation_id` 一律 404。

恢复顺序：**先查 `operation-results`，再决定重试**。查到就按结果走；查不到不代表未执行，重试必须复用同一个键，不能换新键重复提交。查询与重放都会按当前权限重新校验，撤权后旧结果不再可取。

幂等只保证「同一个键不重复执行」，不改变业务语义：`status=succeeded` 表示请求被受理并完成，不代表业务成功（例如 AI 识别失败时任务仍会以 `202` 受理、`task.state=failed`）。

以下入口**刻意不要求**幂等键，原因见第 8 节：`POST /files`、五个照片接口、`POST /imports`（上传，幂等边界在 `POST /imports/{id}/confirm`）。

## 4. 状态码与错误码

**没有 400。** 实际使用：`200/201/202/204/206`、`401/403/404/409/413/422/429/503/500`。入参错误一律 422，路径里的资源不存在一律 404。

| HTTP | code | 含义 | 客户端动作 |
|---|---|---|---|
| 401 | `UNAUTHENTICATED` / `SESSION_EXPIRED` | 未登录 / 会话失效 | 清会话回登录 |
| 403 | `FORBIDDEN` | 无权限 | 展示原因 |
| 403 | `FEATURE_DISABLED` | 该库的对应功能开关已关闭，`message` 给中文原因 | 展示原因，隐藏/禁用入口 |
| 404 | `NOT_FOUND` | 不存在、对当前账号不可见，**或路径里的 id 不是 UUID** | 展示不可访问 |
| 409 | `VERSION_CONFLICT` | 乐观锁冲突 | 刷新后由人确认 |
| 409 | `IDEMPOTENCY_CONFLICT` | 同键不同内容 / 对象已被处理 | 换新键重发 |
| 409 | `INSUFFICIENT_STOCK` `TREE_CYCLE` `NODE_IN_USE` `OPEN_BUSINESS` `PHOTO_ALREADY_LINKED` `FILE_IN_USE` | 具体业务阻止原因 | 展示 `message` |
| 413 | `PAYLOAD_TOO_LARGE` | JSON body 超过 1MB | 改小请求，不重试 |
| 413 | `FILE_TOO_LARGE` | 上传文件超过 10MB（照片与导入共用） | 换更小文件 |
| 422 | `VALIDATION_FAILED` | 缺字段、类型错、body 里的 UUID 非法、`creation_ref` 非 UUID | 修输入后重试 |
| 422 | `INVALID_STATUS` `INVALID_LOCATION` `INVALID_TRANSFER_TARGET` `INVALID_IMAGE_COUNT` | 业务输入校验（枚举、位置、转库目标、图片数量） | 修输入后重试 |
| 422 | `INVALID_IDEMPOTENCY_KEY` | 幂等键不是 UUID 或超长 | 换键 |
| 429 | `RATE_LIMITED` | 限流 | 按 `Retry-After` 等待 |
| 503 | `SERVICE_UNAVAILABLE` `MAINTENANCE` | 依赖不可用 / 维护中 | 显示恢复入口，可重试 |
| 500 | `INTERNAL` | 服务内部错误（不泄露 SQL 细节） | 可重试，持续出现请查日志 |

校验类 `message` 是「中文 + 字段名」，例如「缺少必填字段 space_id」「字段 space_id 必须是合法 ID」，可直接展示给用户。

路径参数与请求体分工：**路径 id 不是 UUID → 404**（路由级守卫，不会 500）；**body 里的 UUID 字段非法 → 422**（在进 SQL 之前拦掉）。

`NOT_IMPLEMENTED` 不是服务端会返回的码（当前代码 0 处产生），客户端保留该分支只是前瞻兜底；只有它允许显示「功能未开放」。

## 5. 物品、状态与可用动作

物品状态枚举：`in_stock`（在库）、`pending_stock`（待入库）、`reserved`（预留）、`maintenance`（维修中）、`sold`（已售）、`scrapped`（已报废）、`lost`（已遗失）。

`GET /api/v1/items?status=in_stock,sold`（逗号分隔，也支持重复参数；空 = 全部）。非法值 → `422 INVALID_STATUS` 并列出全部枚举；`total` 是筛选后的数量，不受分页影响。

`GET /api/v1/items/{id}` 与 `POST /api/v1/items`（201）额外返回：

```json
"allowed_actions": {"transfer": true, "sale": false, "scrap": true, "maintenance": true,
                    "stocktake": true, "photos": true, "export": true},
"action_blocked_reasons": {"sale": "该库已关闭出售功能"}
```

- `allowed_actions` **只反映库级功能开关**，不反映物品业务状态：已售/已报废/维修中的物品仍可能是七键全 `true`，真正的拦截由 `409 OPEN_BUSINESS` 给出。
- `action_blocked_reasons` 只包含值为 `false` 的键。
- 客户端按 `=== false` 禁用按钮并用 `title` 展示原因；字段缺失或为 `null` 时视为可用。列表接口不填这两项。

物品与库存：

- `POST /api/v1/items` 的 `initial_location_id` 可选。不传 → `quantity="0"`、状态 `pending_stock`、没有余额行；传了 → 初始数量按 1 建，并写入 `on_hand=1` 的余额行。
- 库内移位用 `POST /api/v1/inventory/operations`（`kind` 支持 `in`/`out`/`move`/`scrap`/`lost` 等），**不改物品所属库**；换库用转库接口。
- 同库转库 → `422 INVALID_TRANSFER_TARGET`；目标位置不存在 → `404`。
- 库存流水详情是 `GET /api/v1/operations/{id}`（不是 `/inventory/operations/{id}`）。

## 6. 照片

| 方法与路径 | 说明 |
|---|---|
| `POST /api/v1/items/{id}/photos` | body `{file_ids: [...], primary_file_id?}`，追加关联；响应返回全量 `photos` |
| `GET /api/v1/items/{id}/photos` | 全量照片，按 `sort` 升序；无照片返回 `[]`；非成员 404 |
| `PUT /api/v1/items/{id}/photos/order` | body `{file_ids: [...]}`，必须是该物品当前全部照片的一个完整排列，否则 422 |
| `PUT /api/v1/items/{id}/photos/{file_id}/primary` | 设主图 |
| `DELETE /api/v1/items/{id}/photos/{file_id}` | 解除关联（不删文件）；主图被解除时顺延给下一张 |

照片元素形如 `{file_id, is_primary, sort, url}`。四个写接口**不需要** `Idempotency-Key`：重复关联同一文件天然幂等，排序/主图是整体替换。

规则：同一个 `file_id` 已关联到别的物品 → `409 PHOTO_ALREADY_LINKED`，原关联不动；文件属于别人的私有区或另一个库 → `403 FORBIDDEN`「文件不属于该库」；入参错误 → `422 VALIDATION_FAILED`。

上传与文件：`POST /api/v1/files`（multipart，字段名 `file`）→ 201 `{data: {id, ...}}`；`GET /api/v1/files/{id}/content` 与 `/thumbnail` 受上传者与物品归属双重校验；`DELETE /api/v1/files/{id}` 仅上传者本人且未关联时 204，已关联 → `409 FILE_IN_USE`，他人或不存在 → 404。**上传成功不等于已关联**，未关联的文件只有上传者可见。

## 7. AI 识别与导入

AI：

- `GET/PUT /api/v1/ai/settings`：读取/修改 `max_images`（默认 8，上限 32）等配置。修改是**部分更新**：只传要改的字段，未传的保持不变；显式传 0 或负数 → 422。
- `POST /api/v1/ai/tasks`：body `{space_id, file_ids}`，`202` 受理，返回 `{task, candidates}`。`file_ids` 超过 `max_images` → `422 INVALID_IMAGE_COUNT`。AI 提供者限流或超时不会变成 429/503，而是 `202` + `task.state=failed` + 可读的 `task.error`（该字段没有 `error_code`）。
- `POST /api/v1/ai/candidates/{id}/confirm`：body `{space_id, location_id, name?, template_key?, category_id?, fields?, quantity?, photo_ids?, share_photos?}`，响应 `data` **恰好三个键**：

```json
{"data": {"item_id": "...", "public_code": "...", "movement_id": "..." }, "request_id": "..."}
```

`movement_id` 在「待入库」时为 `null`。照片语义：`photo_ids` 传数组 → 只关联所列文件；传 `[]` 或 `share_photos=false` → 明确不关联；两者都不传 → 共享该候选的全部来源图片。空数组不等于未传，客户端必须显式表达意图。

导入：

- `POST /api/v1/imports`（multipart）：`space_id`、`mode`（`catalog` 只建档案 / `stock` 直接入库）、`location_id`（`mode=stock` 必填，缺失 → `422 INVALID_LOCATION`）、`template_key?`、`file`。CSV/XLSX，最大 1000 行、10MB。
- `GET /api/v1/imports/{id}`：批次与逐行结果，行状态为 `catalog` / `stock` / `failed`，并带 `item_id`、`public_code`、`error_code`、`message`。
- `POST /api/v1/imports/{id}/confirm`：`Idempotency-Key` 必填。成功行不会因重试重复建档；失败行可通过「修正文件后重新上传」重来（会产生新批次）。全部成功的批次再确认 → `409 OPEN_BUSINESS`。
- 导出：`POST /api/v1/exports` 建任务，`GET /api/v1/exports/{id}` 取文件。

## 8. 已知限制（设计选择，不要当缺陷修）

- `GET /items` 不支持 `space_id` 过滤：传了会被静默忽略（实例成员本来就可见全部可见库）。
- 请求体里的未知字段静默忽略，字段名拼错不会报 422。
- `POST /imports`（multipart）**不能同键重放**：body 摘要覆盖原始字节，multipart boundary 每次都变 → 同键会被判为异内容而 409。幂等边界在 `POST /imports/{id}/confirm`。
- `POST /files` 刻意不挂幂等：大文件做 body 摘要代价过高，且与「上传≠关联」模型冲突。响应丢失可能留下未关联文件，用 `DELETE /files/{id}` 清理。
- `GET /locations` 是**全实例共享的基础数据**（单户部署的设计选择，不按库过滤）；位置只校验「存在且未删除」，不校验库归属。
- `GET /jobs` 是内部队列，客户端零调用，仅实例管理员可读；没有 `GET /jobs/{id}`。
- 并非所有入口都有 1MB body 上限：`PUT /spaces/{id}/settings`、`/spaces/{id}/fields` 与借还相关入口使用裸 JSON 绑定，没有该保护。
- `/loans/*`、`/sales` 未挂载（返回 404），后续再评估；`GET /spaces/{id}`、`GET /categories/{id}`、`GET /locations/{id}` 未注册，客户端从列表取。
- 规格边界：≤10 用户、<1000 件物品、≤5000 张照片；图片 10MB、JSON body 1MB、导入 1000 行。

## 9. 变更流程

`api/openapi.yaml` 是唯一定义来源。改接口先改 OpenAPI，再改实现与两端客户端；破坏性改动必须同时更新本文件、OpenAPI 与调用方，不做「只改服务端、客户端自适应」的兼容层。新增错误码或状态码也要同步本文件第 4 节的表。
